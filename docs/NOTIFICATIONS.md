# Notifications: what is delivered, how, how fast, and what can never be

This is the operational half of the answer to the standing requirement *"generate an
alert/notification when a potential discrepancy is detected"*
([PROJECT_PROMPT.md](../PROJECT_PROMPT.md) item 6). The analytical half — whether
detection is possible at all — is [ALERTING.md](ALERTING.md) and
[FEASIBILITY.md](FEASIBILITY.md).

**Everything asserted here was measured in this repository on 2026-10-07.** Numbers
come from the committed data files; the one live delivery is linked.

---

## 1. The short answer

**Yes — and it is built, wired and has been proven to fire once against the real
GitHub API.** For the class of discrepancy the NHL publishes an official statement
about (every Coach's Challenge and video review, February 2016 → today) the system
detects the change, writes it to a feed, and pushes it to a subscriber. For the class
it does not publish (why a scorer or an assist was changed, and any correction that
happened and was overwritten between two of our polls) **no notification system can
exist**, because there is nothing to observe. The boundary is drawn in §5, and it is
drawn from evidence rather than from preference.

## 3. What is delivered, and where

Four channels live in [`pipeline/nhl_scoring/notify.py`](../pipeline/nhl_scoring/notify.py).
The table below is **generated by that module** (`notify --describe`) and rendered on
the site's Alerts tab, so the page cannot advertise a channel the code does not have.

| Channel | State today | Needs | What a subscriber does |
| --- | --- | --- | --- |
| Website feed + RSS | **on** | nothing | Open the Alerts tab, or subscribe to [`data/alerts.xml`](../data/alerts.xml) |
| GitHub issue | **on in Actions** | `GITHUB_TOKEN` with `issues: write` (automatic inside a workflow) | Watch the repository → Custom → Issues |
| Webhook (Slack/Discord/any) | off | `SDN_WEBHOOK_URL` secret | Add the secret; the payload carries both `text` and `content` |
| E-mail digest | off | `SDN_SMTP_HOST/PORT/USER/PASSWORD/FROM/TO` secrets | Add the secrets; the digest goes to `SDN_SMTP_TO` |

Every detection workflow now ends with the same delivery step:

```
PYTHONPATH=pipeline python3 -m nhl_scoring.cli notify \
  --channels feed,issue,webhook,email --allow-failure
```

wired into [`situation-room.yml`](../.github/workflows/situation-room.yml) (the primary
path, cron `11,41 * * * *`), [`monitor.yml`](../.github/workflows/monitor.yml) (cron
`*/5`), [`scoring-monitor.yml`](../.github/workflows/scoring-monitor.yml) and
[`backfill.yml`](../.github/workflows/backfill.yml).

those, so the distinction is auditable rather than assumed.

### Delivery rules (each one answers a failure this project already had)

1. **Deliver once.** A fingerprint of title + body + severity + links + goal-total flag
   is stored per alert. An unchanged alert is never re-sent; a schedule that fires 48
   times a day would otherwise re-announce the same 18 alerts 48 times.
2. **A revised alert is news.** If the record behind an alert changes, the fingerprint
   moves and the subscriber is told again, with `[UPDATED]` in the subject.
3. **A failed send is not a delivery.** A 401 or a dead webhook leaves the alert in the
   "new" set, records `retry_next_run`, and the next run retries it. Nothing is marked
   delivered that was not accepted.
4. **One issue per goal-total change, one digest for the rest**, capped at 10 per run.
   A backfill cannot flood the tracker.
5. **An unconfigured channel is reported as `skipped` with the variable that turns it
   on** — never silently dropped, never claimed as sent.
6. **Every delivery writes a committed report.** An outage is visible in git.

## 4. Latency — what is measured, and what is not

| Segment | Measured value | Evidence |
| --- | --- | --- |
| Play → league statement | **minutes** (three samples: CGY@VAN 2026-10-03, EDM@VAN 2026-10-01 ≈20 min, NSH@TOR 2026-10-06) | [`docs/SITUATION_ROOM.md`](SITUATION_ROOM.md) §2, timestamps in the ledger |
| Statement → our ingest | bounded by the cron slot (`:11`/`:41` UTC) **plus** GitHub's scheduler throttle | run history; see below |
| Ingest run time | 20m47s for a **full** 45-page re-read; ~1 minute incremental | run 37684176985 |
| Alert → subscriber | one HTTP request after the run finishes | the delivery report |

Two honest caveats, both measured rather than assumed:

* **GitHub Actions cron is best-effort.** This repository measured *one scheduled run
  in eleven hours* for a `*/5` cron while it was idle. An active repository is
  scheduled far more reliably, but the floor is minutes, not seconds, and nobody should
  design a settlement process around it.
* **The end-to-end number for "how late did we see a statement" has not been measured
  yet.** Every record stores the statement's `content_date` and our `detected_at`, so
  the distribution becomes available as scheduled runs accumulate. **No figure is
  quoted here until it is.**

For anything that must be faster than a scheduler, the ingest is a single command:
`gh workflow run "Situation Room ingest"` from an external timer, or the same module on
an always-on host.

## 5. What can never be notified, and why

| Not detectable | Why | What the system does instead |
| --- | --- | --- |
| **Why a scorer or an assist was changed** | There is no official feed of scoring corrections. A request for one (`/v1/corrections`, `/v1/gamecenter/<id>/situations`) returns **404** — probed in CI, not remembered | Recorded only when the league says it in words (3 records, from `OFFICIAL SCORING CHANGE` posts); otherwise `reason.text = null` plus a flag |
| **A correction made and overwritten between two polls** | The league publishes state, not history. If every capture postdates the correction, the original state exists nowhere this project can read | The archive census exists for exactly this; it can only recover changes bracketed by two captures |
| **Reviews before February 2016** | The statement feed starts 2016-01-15 (earliest statement published 2014-09-02 for a pre-season game). Earlier reviews leave no official machine-readable trace | The frozen-era census compares a game-night HTML report against the current database; it finds *scoring* differences, not review rulings |
| **902 statements that state the result but not the on-ice call** | The prose does not say what was called on the ice, so no change can be inferred without reading it | Kept in the ledger, **not** turned into records, unless a documented human read supplies the on-ice call (2 so far, each with its source on the record) |
| **Which of two disagreeing official artifacts is right** | 12 overturned calls conflict with the play-by-play; the HTML sheet and the GameCenter JSON are the same data rendered twice, so neither arbitrates the other | Flagged `pbp_conflicts_with_situation_room_statement`, never auto-resolved |
| **Whether a bookmaker regraded a settled market** | House rules are private | Settlement exposure is a *class* judgement taken verbatim from the record, with its window (`in_game` vs post-final) |
| **An authoritative "corrected at" timestamp** | The league gives publication times, not correction times | `when_corrected` is an enum plus `timing_uncertain` when inferred |

## 6. Failure modes, and what happens in each

| Failure | Behaviour | Where you would see it |
| --- | --- | --- |
| GitHub token missing or revoked | `issue: skipped` / `failed:401`; the alert stays new and is retried; the feed still publishes | delivery report + `failed_channels` |
| Label does not exist | The delivery layer **creates it** (this is why the old `gh issue create --label detection` step never worked — the label did not exist and a `|| echo` swallowed the error) | report shows the issue anyway |
| Webhook endpoint dead | `webhook: failed:<status>`; the issue channel still runs | report |
| SMTP secrets absent | `email: skipped` with the variable names | report and the site's channel table |
| Feed empty | Exit 0 with "nothing to deliver" — an empty feed is not an error | run log |
| Detector crashes before delivery | Nothing is delivered, and the missing report is itself the signal | absent `data/notifications/last_run.json` |
| Scheduled run throttled by GitHub | Alerts arrive late, in a batch, still deduplicated | run history |

The workflow that ingests the feed runs delivery with `--allow-failure` so a
notification outage can never cost the data, and then **fails the run** if a channel
failed — after the commit, so nothing is lost either way.

## 7. Subscribe in one minute

1. **Issues (recommended):** on the repository, *Watch → Custom → Issues*. Every
   goal-total change opens its own issue with the official links; attribution-only
   changes arrive as one digest.
2. **RSS:** point any reader at
   `https://buffedlizard55-lab.github.io/ScoringDiscrepNHL/data/alerts.xml`.
3. **Slack/Discord:** create an incoming webhook, add its URL as the repository secret
   `SDN_WEBHOOK_URL`. One POST per run, newest alerts first, both `text` and `content`
   set so either flavour renders it.
4. **E-mail:** add the six `SDN_SMTP_*` secrets. GitHub Actions has no mail relay of its
   own, which is why this channel is off until an operator supplies one.

No channel requires editing code, and no credential is stored in this repository.

## 8. Verify it yourself

```bash
PYTHONPATH=pipeline python3 -m nhl_scoring.cli notify --describe      # the channel table
PYTHONPATH=pipeline python3 -m nhl_scoring.cli notify --dry-run       # what would be sent, sending nothing
python3 -m unittest tests.test_notify -v                              # 40 delivery tests, all offline
node tools/check_engine_site.mjs                                      # the published page really renders it
cat data/notifications/first_delivery_2026-10-07.json                 # the one delivery that has happened
```

`tests/test_notify.py` asserts on the wire, not on intentions: the URL, the
`Authorization` header, the JSON body, the labels, the deliver-once behaviour across
two runs, the retry after a 401, and the workflow wiring (a workflow that renders
alerts but never delivers them fails the suite).

## 9. What is still missing

1. **No measured end-to-end latency distribution yet** — needs a week of scheduled runs.
2. **Webhook and e-mail have never been exercised against a real endpoint.** The code
   paths are unit-tested with injected transports; only the GitHub issue channel has
   been proven live. Turning either on is a secret, not a change.
3. **Scorer/assist corrections still depend on the league's announcements**, which are
   not exposed as a feed. Until there is an official one, that class is hours late and
   partially manual.
4. **Delivery is per-alert, not per-market.** A subscriber who cares only about a
   specific team or a specific market still has to filter; the feed carries the fields
   (`teams`, `settlement_window`, `affects_goal_total`) but the channels do not yet
   route on them.
